# 익명 신고 조작 및 과다 저장 방지

## 적용 범위
기존 공개 RPC 이름/인자와 익명 참여를 유지한다. 새로운 개인정보/IP를 수집하지 않는다. 제한은 브라우저가 아니라 DB 함수 안에서 처리하므로 기기 ID·이름 변경 및 Supabase 직접 호출에도 적용된다.

익명 신고는 개인 화면 가림 + 관리자 검토 접수로 바꾼다. 익명 신고 수만으로 공용 글을 자동으로 숨기지 않는다. 이전에 숨겨진 글은 자동 복원하지 않는다. 관리자는 `/admin/#report`에서 신고 내용을 보고 전체 숨김/공개 유지/복원을 선택한다. 일반 로그인 사용자도 DB admins 목록에 없으면 처리 불가.

## 저장 한도
카운터가 처음 생성되거나 만료 후 갱신되는 순간부터 계산하는 기간이다. 달력 날짜 기준이 아니다. 기존 1인/기기별 제한과 방 정원도 함께 적용된다.

| 작업 | 대상별 제한 | 서비스 전체 제한 |
|---|---|---|
| 선물 보내기 | 방당 10개/60초, 60개/1시간 | 120개/60초, 3,000개/24시간 |
| 맨션 벽보 | 맨션당 10개/60초, 60개/1시간 | 120개/60초, 3,000개/24시간 |
| 맨션 입주 | 맨션당 6건/60초, 12건/1시간 | 120건/60초, 3,000건/24시간 |
| 산사 연등·기와 | 기존 기기당 10개/24시간 유지 | 30개/60초, 300개/1시간, 1,000개/24시간 |
| 산사 신고 | 글당 10건/24시간, 동일 기기 재신고 무시 | 30건/60초, 300건/24시간 |
| 방문·행동 통계 저장 | 기존 방문 중복 제거 유지 | 600건/60초, 20,000건/24시간 |
| 번뇌 카운터 증가 | — | 60건/60초, 3,000건/24시간 |

한도 초과 시 콘텐츠 쓰기는 저장 없이 `rate_limit:` 오류를 반환한다. 영문 산타/맨션에도 재시도 안내를 추가했다. 통계·번뇌 카운터는 기존 프런트가 오류를 삼키므로 사용자의 놀이 자체는 계속된다. 이는 소규모 서비스의 초기 저장 보호 한도이며 실제 이용량에 맞춰 조정해야 한다.

## 구현
- 비공개 `abuse_guard` 스키마의 buckets 테이블: bucket/기간별 한 행, 만료 시 재사용. API 역할에는 스키마 및 함수/테이블 권한 없음. RLS 활성.
- INSERT ON CONFLICT의 조건부 UPDATE로 카운터 증가와 한도 검사를 원자적으로 처리. 동시 요청도 같은 카운터를 초과해 성공할 수 없음.
- 전체 제한 검사 때 2일 이상 만료된 행을 최대 50개씩 정리. SKIP LOCKED로 정리 충돌 방지.
- 공개 함수와 같은 트랜잭션이므로 저장 실패 시 할당량 증가도 롤백. '성공한 저장량' 제한이며 모든 실패 요청/읽기 요청을 차단하는 네트워크 제한은 아니다.
- 관리자 검토 함수 2개는 anon 실행 권한을 제거하고 내부 is_admin() 검사. 기존 항목에 reviewed_at 추가. 최근 신고 대상 100개를 검토 대기 우선으로 표시.

## 검증
- `verify-anonymous-abuse.sql`: 실제 DB 적용 전 롤백 리허설 및 적용 후 19개 회귀 검사 통과. 합성 사용자/선물방/맨션/글/신고/카운터를 생성해 검사 후 전체 ROLLBACK. 기존 사용자의 본문이나 계정 정보를 읽지 않음.
- 기기/이름을 바꾼 추가 쓰기 차단, 익명 신고 2건의 자동 숨김 방지, 중복 신고, 비관리자 거부, 관리자 숨김/복원, 기간 만료, 정상 선물 저장 확인.
- `tests/moderation-dom.cjs`: DOM 기반 입력 이스케이프, 취소, 숨김/복원, 권한 오류 후 버튼 복구, 빈 목록/목록 오류 상태 통과. linkedom@0.18.12 사용.
- inline JavaScript 및 santa/mansion 구문 검사 통과.
- `tests/moderation.cjs`: Playwright 브라우저 회귀 스크립트 제공. 현재 실행 환경에서 브라우저 소켓 생성이 차단되어 브라우저 시각 QA는 미실시. DOM 테스트로 대체했으며 브라우저 테스트 통과로 표기하지 않는다.
- 실제 다중 세션 부하 테스트 및 관리자 소셜 로그인 E2E는 미실시.

## 남은 한계와 운영 질문
1. 대량 요청을 서버에 도착하기 전에 차단할 방화벽/봇 방어를 설정할 수 있는가? 현재 Vercel 연결은 moodnight 팀의 온결 프로젝트 2개만 반환하며 moodnight-site 조회는 404. 해당 프로젝트 접근 권한 연결 후 진행해야 한다.
2. CAPTCHA 또는 서버 게이트웨이를 추가할 것인가? 기기 ID는 신원 증명이 아니므로 한도 안에서의 스팸과 신고 자체의 진위는 보장하지 않는다. 직접 Supabase RPC도 우회하지 못하도록 게이트웨이 인증 및 기존 RPC 권한 변경을 함께 설계해야 한다.
3. 정상 이용자들이 공통 한도에 걸리는가? 전체 한도를 악성 사용자가 소진하면 정상 사용자도 기다리게 된다. 로그/규모를 보고 조정하며 이것을 완전한 DDoS·비용 방지라고 설명하면 안 된다.

참고: https://www.postgresql.org/docs/current/sql-insert.html#SQL-ON-CONFLICT (원자적 UPSERT), https://supabase.com/docs/guides/database/postgres/row-level-security (DB 접근 제어).
